DATE: 2026-09-06
SUGGESTION ID: PL-013
TITLE: Rate limiting on auth endpoints (login/signup brute-force defense)

WHAT WAS FOUND: loginAction/signupAction accepted unlimited attempts;
  scrypt made online guessing slow but not free; OAuth callback token
  exchange was also unbounded. The PL-007 limiter was generic and ready
  to reuse — only auth-specific wiring was missing.

WHAT WAS CHANGED: New src/lib/security/request-key.ts
  (clientIpFromHeaders — x-forwarded-for first hop, x-real-ip fallback,
  "local" for direct access; retryMinutes). authRateLimit() guard in
  src/lib/auth/actions.ts: login keyed per-email (5/15min, NAT-safe)
  plus per-IP (30/15min); signup per-IP (5/hour). Google OAuth callback
  limited 10/15min per IP, fail-closed → /login?error=google_rate:<m>
  with a friendly banner (new resolveAuthError parser on the login page).

FILES/MODULES AFFECTED: src/lib/auth/actions.ts,
  src/app/auth/google/callback/route.ts, src/app/login/page.tsx,
  src/lib/security/request-key.ts (new), tests/request-key.test.ts (new),
  scripts/tmp-auth-throttle.mjs (temporary, removed).

WHY THE CHANGE WAS MADE: Online brute force against login (and abuse of
  the callback's outbound calls) had no cost ceiling. Limits are
  deliberately generous because the user accesses via a shared LAN IP.

TESTS PERFORMED: 6 new unit tests (37 total, all pass) covering XFF
  parsing, fallbacks, NAT keying and retry-minute rounding. Live browser
  hammer test through the real login form: attempts 1-5 → normal auth
  error; attempt 6+ → "Too many sign-in attempts … 15 minute(s)";
  different email on same IP → unaffected; zero console errors. tsc;
  build; smoke 14/14.

VERIFICATION RESULT: all green; live throttle behavior matches design
  exactly (server-side debug line confirmed counts climb 1→5 then block).

REGRESSION CHECK: full gates re-run after removing debug logging —
  tsc clean, 37/37 tests, build OK, smoke 14/14.

NEW ISSUES DISCOVERED: the live test initially LOOKED like the limiter

  calling requestSubmit() while the submit button was disabled mid-

  matched. Lesson recorded: anchor UI tests on the pending cycle
  (spinner appear → clear), never on stale DOM text.

NEW SUGGESTIONS CREATED: none (post-audit found no new debt; the

ENTRY #14 — PL-008: Streaming AI chat (token-by-token)

DATE: 2026-09-06
SUGGESTION ID: PL-008
TITLE: Stream AI chat responses token-by-token

WHAT WAS FOUND: Chat awaited the complete validated JSON reply before
  rendering anything (one server action, no streaming route). Provider
  abstraction had no streaming capability.

WHAT WAS CHANGED:
  - src/lib/ai/types.ts: AIProvider gained optional stream(system, user,
    opts, onDelta) — providers without it fall back to complete().
  - src/lib/ai/provider.ts: OpenAICompatibleProvider.stream() parses
    OpenAI-dialect SSE (Groq-compatible), emits onDelta per token,
    accumulates the full text, skips malformed keepalive frames.
  - src/lib/ai/router.ts: prompt construction extracted into exported
    llmChatParams(ctx, message, intent, history, mode: "json" | "text")
    shared by both transports (JSON-mode line only in json mode); added
    exported isLlmIntent()/detectIntent reuse. freeformOrTutor now calls
    the shared builder — zero prompt drift between paths.
  - src/app/api/chat/route.ts (NEW): SSE route. Chain identical to the
    action: currentUser auth -> 2000-char zod validation -> per-user rate
    limit -> sanitizeUserText -> persist user msg -> stream. Deterministic
    intents stream one chunk then done{}; LLM intents stream deltas then
    done{} (authoritative, carries validated meta actually persisted);
    any failure emits error{} and closes cleanly; empty stream falls back
    to the deterministic responder so the conversation never dies.
  - src/components/app/chat-view.tsx: send() uses fetch + ReadableStream
    reader, appends delta frames into state (thinking indicator swaps to
    growing bubble on first delta), done record is authoritative (final
    content + actions/suggested + session list update). 401/429/400
    handled with honest toasts. Server action removed from client.

FILES/MODULES AFFECTED: src/lib/ai/types.ts, src/lib/ai/provider.ts,
  src/lib/ai/router.ts, src/app/api/chat/route.ts (new),
  src/components/app/chat-view.tsx

WHY THE CHANGE WAS MADE: Perceived latency for tutor/freeform replies
  dominated by model generation time; streaming shows text as it is
  produced. Explicitly requested by the user (PL-008).

TESTS PERFORMED: tsc --noEmit clean; eslint 0 problems; 37/37 vitest;
  next build OK; smoke 14/14; LIVE E2E against production server with
  real Groq key: deterministic intent -> delta+done framing; LLM intent
  -> 349 delta frames, first token 7ms, last 698ms, reply grounded in
  the student's real weak topics; no error events.

VERIFICATION RESULT: STREAM E2E: PASS (script asserted >=3 deltas and
  a non-empty done reply; observed 349).

REGRESSION CHECK: Server-action path kept as fallback (action still
  exported for any non-UI callers); full gate suite re-run green after
  all edits; smoke confirms all app pages still render.
