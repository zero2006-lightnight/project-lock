SUGGESTION ID: PL-001
TITLE: Fix Secure-cookie rejection on plain-HTTP LAN hosts (onboarding bounce-to-login)
CATEGORY: Bug / Security
PRIORITY: P1 — Critical
CURRENT STATUS: COMPLETED
CURRENT IMPLEMENTATION STATE: src/lib/auth/session.ts sets the session
  cookie `Secure` only when the request is actually HTTPS (derived from
  x-forwarded-proto, not NODE_ENV).
PROBLEM: In production builds the session cookie was always `Secure`.
  Browsers silently reject Secure cookies over plain HTTP on
  non-localhost hosts (e.g. http://192.168.56.1:3000). Signup worked but
  the cookie was dropped, so "Generate my plan" hit the server with no
  session and bounced the student to /login. Only LAN-IP access was
  affected; localhost was exempt, which is why dev testing passed.
PROPOSED IMPROVEMENT: Derive the cookie Secure flag from the real
  request protocol.
EXPECTED BENEFIT: Onboarding completes on LAN-IP HTTP deployments.
DEPENDENCIES: none
RISK: Low — Secure is still set on HTTPS; proxy deployments must send
  x-forwarded-proto (documented in README troubleshooting).
SCOPE: src/lib/auth/session.ts
VERIFICATION METHOD: Cookie-level CDP browser trace + full signup →
  onboarding → dashboard E2E on http://192.168.56.1:3000.
UPGRADE OPPORTUNITY: none needed
IMPLEMENTATION NOTES: Found via browser cookie trace (0 cookies stored
  after signup pre-fix; sp_session secure=false post-fix).

SUGGESTION ID: PL-007
TITLE: Per-user rate limiting + prompt-injection hardening on the AI chat endpoint
CATEGORY: Security
PRIORITY: P1 — Critical
CURRENT STATUS: COMPLETED
CURRENT IMPLEMENTATION STATE: sendChatMessageAction enforces
  20 messages / 5 min per user (in-memory sliding-window limiter,
  src/lib/security/rate-limit.ts — rejected hits consume no budget so
  blocks never self-extend). User text is control-char-stripped and
  identical-line-collapsed (src/lib/security/guard.ts), delimiter-wrapped
  <<<USER_MESSAGE>>>…<<<END_USER_MESSAGE>>>, and the system prompt carries
  an untrusted-input directive. Unit-tested in tests/security.test.ts
  (31 tests project-wide).
PROBLEM: Two exposures on the one endpoint that spends money and talks
  to a model: (1) no per-user rate limit, (2) prompt-injection surface —
  a crafted message could try to override Pilot's instructions. Blast
  radius is bounded by design (LLM has no tool/DB-write access; outputs
  Zod-validated), but both gaps should still be closed.
PROPOSED IMPROVEMENT: Sliding-window per-user limiter at the action
  boundary + defense-in-depth input hygiene (strip control tokens,
  wrap user text in delimiters, add an untrusted-input directive to the
  system prompt). No heuristic message refusal — false positives would
  harm UX more than the risk they mitigate.
EXPECTED BENEFIT: Bounded per-user cost; neutralized instruction-
  override attempts; clear feedback when throttled.
DEPENDENCIES: none (in-memory limiter by design for the single-instance
  SQLite deployment; a shared store becomes relevant with multi-instance
  Postgres — see PL-009).
RISK: Low.
SCOPE: new src/lib/security/*, src/lib/actions/chat.ts,
  src/lib/ai/router.ts, tests.
VERIFICATION METHOD: Unit tests for limiter windows/limits and guard
  behavior; chat E2E regression (scripts/ai-qa.mjs) still green; full
  gates (tsc, vitest, build, smoke).
UPGRADE OPPORTUNITY: Reuse the same limiter on auth endpoints (split
  into PL-013 to keep changes isolated).
IMPLEMENTATION NOTES: Implemented 2026-09-06. Unit tests caught two
  real bugs in the first draft BEFORE any deployment: (a) blocked hits
  were recorded, extending blocks forever; (b) spam collapse kept 2 of
  3 identical lines. Both fixed and re-tested. LLM chat E2E regression
  (scripts/ai-qa.mjs, DB ground-truth) green through the secured path.
  Changelog entry #9.

VERIFICATION METHOD: Browser E2E asserting progressive text growth.
UPGRADE OPPORTUNITY: —
IMPLEMENTATION NOTES: Completed. Transport: POST /api/chat (SSE).
  Shared prompt builder (llmChatParams) keeps JSON path and stream path
  wording-identical, with a mode switch (json/text). Provider gained an
  optional stream() with onDelta callback (OpenAI-compatible SSE; Groq
  verified live). Client reads the stream and renders incrementally;
  "done" is authoritative (carries validated + persisted meta). Safety
